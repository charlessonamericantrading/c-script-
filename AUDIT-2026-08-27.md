# Auditoría adversarial — 2026-08-27

Auditoría de todo el compilador/runtime (`compiler/src`), pedida explícitamente por el
usuario antes de seguir con el backlog. Metodología: 5 agentes de solo lectura
(`Explore`, no pueden editar código) en paralelo, cada uno sobre una capa distinta
(concurrencia/panics, consistencia de codegen, auth/secretos, superficie de
`.unwrap()`/panic, capa SQL/DB). Cada hallazgo listado acá fue **verificado a mano**
por mí después, contra el binario real compilado de este mismo árbol — no se
documenta nada solo porque un agente lo reportó. El estado de verificación de cada
uno está marcado explícitamente.

No se tocó ningún archivo de código en esta ronda — es un reporte, no una serie de
fixes. Los fixes quedan para la próxima ronda, priorizados por severidad.

## 1. `crypto.randomToken(length)` con `length` negativo o gigante mata el proceso `linkc serve` entero

**Severidad: Crítica — denegación de servicio total con una sola request, sin autenticación si el rpc no la exige.**

`compiler/src/runtime/mod.rs:2329-2342`:

```rust
"randomToken" => {
    let length = match args.first() {
        Some(Value::Int(n)) => *n as usize,   // negativo -> usize gigante por reinterpretación de bits
        _ => return Err(err("crypto.randomToken requiere un argumento Int")),
    };
    let length = length.max(8);               // solo pone un piso, nunca un techo
    let bytes = os_random_bytes(length.div_ceil(2))?;
    ...
}
```

`os_random_bytes` (`mod.rs:1622-1627`) hace `vec![0u8; n]`. El checker (`checker.rs:3897-3899`) solo valida que el argumento sea un `Int` — a diferencia de `dateFromParts` (§3.90), que sí valida rango y da un 400 limpio, acá no hay ningún límite superior ni chequeo de signo.

**Reproducido en vivo, dos escalones:**

```link
service Gen {
    rpc genCode(length: Int) -> String { crypto.randomToken(length) }
}
```

- `{"length": -1}` → `*n as usize` da `usize::MAX`, `div_ceil(2)` da ~9.2×10¹⁸ bytes — por encima del límite que el macro `vec!` chequea ANTES de pedirle memoria al sistema (`isize::MAX`). Panic normal y catcheable ("capacity overflow"), muere solo el hilo de esa request, el proceso sigue vivo. Confirmado: `health` después sigue en `200`.
- `{"length": 9223372036854775807}` (`i64::MAX`) → `div_ceil(2)` da ~4.6×10¹⁸ bytes, **por debajo** de ese límite del macro, así que el pedido sí llega al allocator real del sistema operativo. Ningún sistema tiene esa memoria — Rust llama a `handle_alloc_error`, que hace `std::process::abort()` **sin poder atraparse con `catch_unwind`, sin importar el hilo**. Confirmado en el log real:
  ```
  memory allocation of 4611686018427387904 bytes failed
  ```
  y el puerto deja de escuchar por completo (`netstat` ya no lo muestra `LISTENING`, solo conexiones viejas en `TIME_WAIT`).

Bajo `serve-all` (§3.92), esto se lleva puesto **todos** los servicios coexistiendo en ese proceso, no solo el que declaró el rpc vulnerable.

**Fix sugerido**: cotejar `length` contra un rango razonable (negativo → error; un techo explícito, por ejemplo unos pocos KB — no hay ningún caso de uso real para un token de gigabytes) ANTES de llamar a `os_random_bytes`, mismo criterio que `crypto.randomInt`/`dateFromParts` ya usan para sus propios límites.

## 2. `@cache` + `@authenticated`/`@requires` filtra datos de un usuario hacia otro

**Severidad: Crítica — fuga de datos entre usuarios autenticados, cero coordinación necesaria del lado del atacante.**

`compiler/src/runtime/server.rs:982-985`, respaldado por `compiler/src/cache.rs` (`CacheStore::get`/`put`): la clave de caché es únicamente `(service, rpc, args_json)`. Nunca incluye el token de sesión, el `userId` ni el rol. El gate de auth (`check_auth_gate`) corre ANTES del lookup de caché, así que solo hace falta *alguna* sesión válida para llegar hasta ahí — no la sesión correcta.

**Reproducido en vivo:**

```link
service Account {
    rpc register(email: String, secret: String) -> User { ... }
    rpc login(id: Int) -> String { auth.createSessionWithId(Role.Member {}, id) }
    @authenticated
    @cache("30s")
    rpc myProfile() -> User? { db.users.find(auth.currentUserId() ?? 0) }
}
```

1. Se registran Alice (id 1, `secret: "ALICE_SECRET"`) y Bob (id 2).
2. Alice llama `myProfile` con su propio token → `{"email":"alice@x.com","id":1,"secret":"ALICE_SECRET"}`, queda cacheado bajo la clave `("Account","myProfile","{}")`.
3. Bob llama `myProfile` con **su propio token válido**, mismo cuerpo vacío `{}` → recibe **el perfil de Alice completo, incluyendo `secret`**, en vez del suyo. Su cuerpo de rpc nunca corrió.

Esto rompe exactamente el patrón que GRAMMAR.md §3.53 documenta y promueve (`auth.currentUserId()` para endpoints personalizados como "mis notas", "mi dashboard"). Cualquier rpc `@authenticated`/`@requires` + `@cache` cuya respuesta dependa de la identidad del caller en vez de sus argumentos es vulnerable — más grave cuanto menos argumentos tenga el rpc (un rpc sin argumentos, el caso más común de "dame mis datos", es el peor escenario: una sola clave de caché para TODOS los usuarios).

**Relacionado, menor**: `@idempotent` (`compiler/src/idempotency.rs`) tiene la misma forma arquitectural — la clave es `(service, rpc, Idempotency-Key)` sin ningún dato de sesión — pero requiere que dos usuarios distintos coincidan en el valor exacto del header `Idempotency-Key` (elegido por el cliente) y el mismo body, mucho más difícil de disparar por accidente que el caso de `@cache`.

**Fix sugerido**: cuando el rpc lleva `@authenticated`/`@requires`, incluir el identificador de sesión (o como mínimo el `userId`) en la clave de caché — o, más simple y más seguro por defecto, rechazar en el checker la combinación `@cache` + `@authenticated`/`@requires` hasta que exista un diseño real de esto (mismo criterio ya usado para otras combinaciones sin sentido, ver `@cron` §3.159).

## 3. `Patch<T>` (usado por `applyPatch`) nunca corre `@validate`/`@check` — bypass real de validación en el camino de escritura más común

**Severidad: Alta — cualquier constraint de `@validate` es enforcement-en-el-papel para toda actualización parcial.**

`compiler/src/runtime/mod.rs`: el brazo `Type::Struct { fields, name }` de `json_to_typed_value` (decodifica el body de una request) llama a `apply_field_validators(...)` después de construir el struct. El brazo `Type::PatchOf(inner)` — el que decodifica el argumento `Patch<T>` de `applyPatch` — construye el struct campo por campo y **nunca llama a esa función**. No hay tampoco ningún respaldo a nivel SQL para `@validate`: `check_clause_sql` (`db.rs`) solo emite `CHECK` de DDL para los `FieldCheck` numéricos/de longitud — `@validate(email)`/`@validate(regex, ...)` no tiene ninguna representación en DDL, así que la llamada de aplicación es el **único** punto de enforcement en todo el sistema, y es justo el que `Patch<T>` se salta.

**Reproducido en vivo:**

```link
type User = { id: Int, @validate(email) email: String, name: String }
db { users: User[] }
service Users {
  rpc create(email: String, name: String) -> User { db.users.insert(User { id: 0, email: email, name: name }) }
  rpc update(id: Int, patch: Patch<User>) -> User { db.users.applyPatch(id, patch) }
}
```

- `POST /Users/create {"email":"not-an-email","name":"Bad"}` → `400`, mensaje claro (`@validate(email)`).
- `POST /Users/update {"id":1,"patch":{"email":"not-an-email"}}` → **`200`**, el valor inválido queda persistido: `{"email":"not-an-email","id":1,"name":"Ada"}`.

Además, `@check` (numérico/longitud) SÍ suele quedar cubierto porque tiene un `CHECK` real de DDL — **excepto en modo `--adopt-existing`**, donde el propio código nunca ejecuta DDL (`db.rs:1069-1078`, el comentario ahí dice explícitamente "la validación de `@check` sigue aplicando del lado de la aplicación... sin importar este modo" — esa afirmación es falsa específicamente para el camino `Patch<T>`).

**Fix sugerido**: `Type::PatchOf(inner)` todavía tiene acceso a `inner`'s `name` — cablear el mismo `field_annotations_for` + `apply_field_validators` que ya usa el brazo `Type::Struct`, tolerando que el patch no traiga todos los campos (la función ya solo valida las claves presentes).

## 4. `@idempotent` tiene una carrera TOCTOU real — dos requests concurrentes con la misma `Idempotency-Key` ejecutan el cuerpo dos veces

**Severidad: Alta — exactamente el escenario que `@idempotent` existe para prevenir (doble cobro, pedido duplicado).**

`compiler/src/runtime/server.rs`: `lookup()` y `store()` son dos adquisiciones de candado SEPARADAS, con el cuerpo entero del rpc (`handle_rpc(...)`) corriendo SIN ningún candado sostenido entre medio:

```rust
match idempotency_store.lock().lookup(...) { Lookup::Miss => {} ... }  // candado #1, se suelta enseguida
...
let (status, ...) = handle_rpc(...);   // <-- sin ningún candado acá
...
if (200..300).contains(&status) { idempotency_store.lock().store(...); }  // candado #2, mucho después
```

Dos requests con la misma `Idempotency-Key` que llegan casi al mismo tiempo ven las dos `Lookup::Miss` (ninguna guardó todavía), y las dos corren el cuerpo — con el modelo de un hilo por request (v1.114.0), esto ya no es un caso teórico.

**Reproducido en vivo:**

```link
type Order = { id: Int, amount: Int }
db { orders: Order[] }
service Payments {
    @idempotent
    rpc charge(amount: Int) -> Order { db.orders.insert(Order { id: 0, amount: amount }) }
}
```

30 requests `POST /Payments/charge` **concurrentes** (mismo `Idempotency-Key`, mismo body) → **2 filas insertadas** para un solo cargo lógico. GRAMMAR.md §3.140 solo documenta y prueba el caso de reintento SECUENCIAL (esperar la primera respuesta antes de reintentar) — nunca el caso concurrente, que es justo el que un cliente con timeout+retry puede producir de verdad.

**Fix sugerido**: un estado `Lookup::InFlight` (reservar la clave, correr el cuerpo, y recién ahí liberar/registrar el resultado, todo bajo el mismo candado, o un mutex por clave) — mismo patrón de "reservar antes de ejecutar" que ya resolvió el problema análogo de `upsert` en v1.115.0.

**Relacionado (#11 en la tabla)**: `@cache` tiene la MISMA forma exacta de carrera (`get`/`put` separados) — pero como `@cache` está pensado para lecturas sin efectos secundarios, el resultado de una ejecución duplicada concurrente es solo trabajo desperdiciado ("estampida de caché"), no una escritura duplicada. Severidad bastante menor, mismo fix si se ataca.

## 5. `insert()` panica en vez de dar un error limpio si la fila se borra entre el INSERT y el SELECT de confirmación

**Severidad: Media-Alta — asimetría clara con el código hermano, panic evitable con un one-liner.**

`compiler/src/runtime/db.rs:1581-1588`:

```rust
let new_id = self.backend.insert_returning_id(&sql, &params).map_err(|e| write_error("insert", e))?;
let inserted = self
    .select_rows(collection, columns, Some(new_id))?
    .into_iter()
    .next()
    .expect("la fila recién insertada tiene que existir");   // <-- panica
```

Comparar con `applyPatch`, la MISMA forma (reconsultar por id después de escribir), unas líneas más abajo (`db.rs:1616-1620`):

```rust
let updated = self
    .select_rows(collection, columns, Some(id))?
    .into_iter()
    .next()
    .ok_or_else(|| RuntimeError::new(format!("no hay ningún elemento con id {id} en '{collection}'")))?;  // <-- error limpio
```

Fuera de un `transaction{}` (el caso común de un `insert` suelto), el INSERT y el SELECT son dos llamadas independientes al backend, cada una con su propio candado — hay una ventana real donde otro hilo (un `deleteWhere` concurrente cuyo predicado matchea la fila recién insertada, por ejemplo por un valor de campo por defecto) puede borrarla antes del SELECT. El `.expect(...)` panica en vez de devolver el `RuntimeError` que el resto del archivo usa consistentemente para esta misma clase de carrera.

**No verificado en vivo** (la ventana de tiempo es muy angosta para forzarla con curl desde afuera de forma confiable) — confirmado leyendo el código, la asimetría con `applyPatch` es inequívoca.

**Fix sugerido**: cambiar el `.expect(...)` por el mismo `.ok_or_else(...)` que ya usa `applyPatch`.

## 6. Agregaciones (`sumBy`/`countBy`/`avgBy`/`maxBy`/`minBy`) panican sobre una columna `NULL` heredada de una migración

**Severidad: Media-Alta — alcanzable en el flujo de evolución de esquema que el propio proyecto documenta como soportado.**

`compiler/src/runtime/db.rs:2625-2650` (`scalar_cell_to_value`, usada por `select_grouped`, el motor de `sumBy`/etc.):

```rust
fn scalar_cell_to_value(ty: &Type, cell: &Cell) -> Value {
    match (ty, cell) {
        ...
        (_, Cell::Bool(b)) => Value::Bool(*b),
        (ty, cell) => panic!("una agregación devolvió {cell:?} para una columna declarada {ty}"),  // sin brazo para Cell::Null
    }
}
```

Contrastar con `row_to_fields` (el decodificador de lectura normal, `find`/`all`/etc.), que SÍ fue reforzado a propósito para convertir un `NULL` inesperado en un `RuntimeError` limpio ("null_but_required") — ese fix nunca se aplicó a este camino de agregación.

**Cadena de alcanzabilidad, confirmada leyendo el código** (no se pudo levantar un Postgres local en este entorno para probarlo de punta a punta):
1. `alter_table_add_column_postgres` (`codegen/postgres_emit.rs:163-173`) genera `ALTER TABLE ... ADD COLUMN IF NOT EXISTS "campo" <tipo>` **sin `NOT NULL` nunca**, sin importar si el campo es requerido en el `.link` — confirmado leyendo la función completa, no arma la constraint bajo ninguna condición.
2. Esto es exactamente lo que la migración no-destructiva contra Postgres promete y documenta (README/llms.txt: "agrega una columna nueva nullable, incluso una requerida").
3. En SQLite, en cambio, sí verifiqué en vivo que el mismo escenario (agregar un campo requerido nuevo a una colección con filas existentes) es rechazado — el servidor se niega a arrancar con un error claro de "schema incompatible", nunca migra en silencio.
4. Entonces: sobre Postgres, una colección con filas viejas + un campo requerido agregado después + una llamada a `sumBy`/`countBy`/`avgBy`/`maxBy`/`minBy` agrupando o valorando por ese campo, sobre una fila vieja (con `NULL` físico ahí) → panic de ese hilo.

**Fix sugerido**: agregar un brazo para `Cell::Null` en `scalar_cell_to_value` devolviendo un `RuntimeError` con el mismo mensaje/criterio que `row_to_fields` ya usa.

## 7. El checker acepta un rpc `@cron` como blanco válido de `@invalidates` — invalidación de caché muerta en silencio

**Severidad: Media — no rompe nada en runtime, pero el checker no cumple su propio trabajo (contrato mentiroso).**

`compiler/src/checker.rs:1818-1852` (`check_invalidates_annotation`) valida el nombre del blanco vía `RpcDecl::looks_like_a_query()`, que devuelve `true` para cualquier rpc con CERO parámetros — y todo rpc `@cron` tiene cero parámetros por construcción (el propio checker se lo exige). El sitio que sí filtra `@cron` correctamente es `ts_emit.rs::emit_hooks` (el que de verdad genera el hook de invalidación), pero el checker nunca hace esa misma exclusión.

**Reproducido en vivo:**

```link
service Jobs {
    @cron("5m")
    rpc sweep() -> Void { }
    @invalidates(sweep)
    rpc create(name: String) -> Item { db.items.insert(Item { id: 0, name: name }) }
}
```

`linkc build` da `OK`. `hooks.ts` generado contiene una llamada muerta para siempre: `invalidateQueryCache(client, "Jobs.sweep")` dentro de `useJobsCreateMutation` — un prefijo de clave de caché que ningún hook escribe jamás, porque `emit_hooks` sí excluyó a `sweep` de generar su propio hook de Query. Inofensivo en runtime (un no-op), pero exactamente la clase de "mentira silenciosa en un artefacto generado" que este proyecto rechaza explícitamente en otros lados (ver el diseño de `@example`, GRAMMAR.md).

**Fix sugerido**: `check_invalidates_annotation` debería excluir explícitamente un blanco con `.cron().is_some()`, mismo criterio que ya usan los 6 sitios de codegen.

## 8. `linkc doc` no muestra badges de auth/rate-limit/deprecated en un `stream`

**Severidad: Media — documentación generada que miente sobre qué está protegido.**

`compiler/src/doc.rs`, el brazo `Member::Stream(st)` de `render_service` solo renderiza un badge estático `📡 Realtime` y nunca mira `st.auth()`/`st.rate_limit()`/`st.deprecated()`/`st.cors()` — a diferencia del brazo `Member::Rpc(r)`, que sí calcula y muestra esos badges. Ninguna anotación de esas está restringida a `rpc` (GRAMMAR.md §3.14 dice explícitamente que auth aplica igual a `rpc` Y `stream`).

Reproducido por el agente contra el binario real (`linkc doc` generando HTML para un `stream` con `@requires(Role.Admin)` + `@rate_limit` + `@deprecated`, mostrando solo el badge de Realtime, sin candado ni advertencia de rate-limit ni de deprecación) — metodología verificada independientemente por mí con un caso equivalente (`lint`, hallazgo #10), no se re-corrió este caso puntual por tiempo.

El enforcement REAL en runtime no está afectado (`required_auth`/`required_rate_limit` sí cubren `Member::Stream` correctamente) — es puramente el documento generado el que desinforma a quien lo lea.

**Fix sugerido**: extraer el cálculo de badges a una función compartida entre los brazos `Rpc` y `Stream` de `render_service`, en vez de tener dos implementaciones independientes.

## 9. `GET /metrics` sostiene el candado de `metrics_store` mientras contiende por el candado de la conexión a la base

**Severidad: Media — no es un deadlock, pero sí un vector de contención/latencia bajo tráfico real.**

`compiler/src/runtime/server.rs:819`:

```rust
let metrics_text = metrics_store.lock().render_prometheus_text(&db.subscriber_counts(), db.size_bytes(), &db.oversized_notify_drop_counts());
```

Por orden de evaluación de Rust, el receptor (`metrics_store.lock()`) se evalúa primero y el `MutexGuard` temporal se mantiene vivo durante TODA la sentencia mientras se evalúan los argumentos — así que `metrics_store` queda tomado mientras `db.size_bytes()` corre (`PRAGMA` real en SQLite, o un round-trip de red `SELECT pg_database_size(...)` en Postgres), que a su vez pide el mismo candado de conexión compartido que `transaction{}`/`upsert` sostienen por toda su duración (incluyendo cualquier `http.*` lento adentro, ya documentado como límite aceptado en §3.158).

Si un `GET /metrics` cae mientras otro hilo está en medio de una transacción larga, ese request queda bloqueado sosteniendo `metrics_store` — y CUALQUIER otro hilo que necesite `metrics_store` (el registro de un rechazo de `@rate_limit`, que corre ANTES de mandar el 429; el registro final de cada request normal) queda en cola detrás, atando hilos del sistema operativo de más (no hay pool, es un hilo por request).

No es un deadlock (nadie sostiene la conexión y después espera `metrics_store`), solo latencia/contención concentrada en tráfico de scraping de `/metrics` combinado con transacciones largas.

**Fix sugerido**: recolectar `db.subscriber_counts()`/`db.size_bytes()`/`db.oversized_notify_drop_counts()` ANTES de tomar el candado de `metrics_store`, y sostenerlo solo para el formateo (que es puro cómputo en memoria).

## 10. `lint`: `mixed-service-auth` da falso positivo cuando un servicio mezcla rpcs protegidos con un job `@cron`

**Severidad: Baja-Media — solo ruido de desarrollo, sin impacto funcional ni de seguridad real.**

`compiler/src/lint.rs:23-28`: `has_auth`/`has_unauth` se calculan sobre TODOS los miembros vía `r.auth()`, sin excluir `.cron()`. Como un rpc `@cron` nunca puede llevar `@authenticated`/`@requires` (el checker se lo prohíbe, es la única anotación permitida), cualquier servicio con al menos un job `@cron` y al menos un rpc protegido dispara el lint, aunque TODOS los endpoints HTTP reales estén protegidos de manera uniforme.

**Reproducido en vivo:**

```link
service Jobs {
    @authenticated rpc me() -> Void { }
    @authenticated rpc me2() -> Void { }
    @cron("5m") rpc sweep() -> Void { }
}
```

```
$ linkc lint jobs2.link
[mixed-service-auth] ... el servicio 'Jobs' mezcla RPCs protegidos por @requires/@authenticated con RPCs públicos sin anotación
```

Dispara justo en el patrón que el propio `@cron` (§3.159) fue diseñado para soportar: una API protegida con un job de limpieza al lado.

**Fix sugerido**: excluir `.cron().is_some()` del cálculo de `has_unauth`, mismo criterio que los 6 sitios de codegen ya usan.

## 11-16. Hallazgos menores / de menor confianza

- **#11 — `@cache` con la misma forma de carrera que `@idempotent`** (ver hallazgo #4): mismo patrón `get`/`put` separado, pero como `@cache` es para lecturas sin efectos secundarios documentadas, el peor caso es trabajo duplicado desperdiciado bajo ráfaga concurrente ("cache stampede"), no una escritura duplicada. Mismo fix si se ataca.
- **#12 — `@unique`/`@index` no son índices parciales respecto a `@softDelete`**: un registro soft-deleted sigue ocupando su slot único en el índice físico — reinsertar un valor único después de "borrar" el original falla con un 400 de violación UNIQUE, aunque para la aplicación (todo camino de lectura filtra el soft-delete) ese valor ya no está en uso. No es una respuesta incorrecta silenciosa (el 400 es honesto), es una limitación de diseño no documentada. Requeriría índices parciales (`CREATE UNIQUE INDEX ... WHERE "deletedAt" IS NULL`) en los dos backends — cambio de arquitectura, no un one-liner.
- **#13 — `--jwt-secret ""` / `--service-api-key ""` (string vacío explícito por flag) activa la feature con secreto vacío**: `read_flag_or_env` (`main.rs:2122-2131`) filtra un valor de ENV VAR vacío (`.filter(|v| !v.trim().is_empty())`) pero NO aplica el mismo filtro al valor que viene de un flag de CLI — confirmado leyendo la función. Requiere que quien opera el servidor pase literalmente una cadena vacía como valor del flag (ej. un script de deploy con una variable de entorno vacía interpolada sin comillas de seguridad) — no explotable a distancia por sí solo, pero una inconsistencia real entre los dos caminos que deberían comportarse igual.
- **#14 — Panics de tipo-incompatible decodificando filas de una tabla `--adopt-existing` con datos legado** (reportado por el agente de superficie de panics, no verificado independientemente por tiempo): varios sitios en `row_to_fields`/`write_param` asumen que un valor JSON guardado fue escrito por el propio programa, y usan `panic!` en vez de `RuntimeError` si eso no se cumple — relevante solo bajo adopción de una tabla preexistente con datos que no calzan con el tipo declarado actual.
- **#15 — Composición de `recordFailedLogin`/`failedLoginCount` tiene una carrera check-then-act inherente**: cada primitivo es atómico por separado, pero GRAMMAR.md §3.152 los documenta explícitamente como piezas para COMPONER a mano (nunca un "check-and-record" atómico) — una ráfaga concurrente de intentos de login puede superar el umbral configurado antes de que el primer `recordFailedLogin` se registre. Probablemente aceptado por diseño (documentar el límite explícitamente en GRAMMAR.md, si no está ya, sería el fix mínimo) — no lo cuento como bug de runtime.
- **#16 — `+`/`-`/`*` sobre `Int`/`Int64` siguen sin `checked_*`**: `numeric_op` (`mod.rs:918-923`) sigue usando `a+b`/`a-b`/`a*b` crudo (solo `/` y `%` se arreglaron en v1.119.0/§3.162). En perfil `release` (el que corren los binarios publicados) esto WRAPPEA en silencio en vez de panicar — un bug de corrección silenciosa, no de estabilidad, en ese perfil. En perfil `dev`/debug si panicara, dentro de `transaction{}`/`@cron` ya queda cubierto por el `catch_unwind` de v1.120.0/v1.121.0; fuera de esos dos, un panic sigue matando solo ese hilo (comportamiento ya aceptado explícitamente en GRAMMAR.md §3.163). No es un hallazgo nuevo, incluido acá solo por completitud del mapa.

## Qué se descartó explícitamente (falsos positivos verificados)

- El histórico bug de `@cron` faltando en UN emisor de TypeScript (§3.162) sigue cerrado — los 6 sitios canónicos de codegen (`ts_emit.rs` ×3, `openapi_emit.rs`, `llms_txt_emit.rs` ×2) tratan `@cron`, `@deprecated`, y toda otra anotación relevante de forma consistente entre sí.
- El orden de candados `subscribers`→conexión sigue siendo consistente en todo `db.rs` — no se encontró ningún ABBA nuevo.
- JWT (HS256, rechazo de `alg` distinto, comparación de firma constant-time), el chequeo de `--service-api-key`, y el `SessionStore` (tokens de 128 bits del CSPRNG del sistema, sin fallback débil) están sólidos — sin hallazgos.
- Ningún sitio de generación de SQL concatena un valor de request directamente en la sentencia — los identificadores de columna/tabla vienen siempre del propio AST (restringidos por el lexer a `[A-Za-z_][A-Za-z0-9_]*`), nunca de un string de usuario.
- `@softDelete` está correctamente filtrado en absolutamente todos los caminos de lectura verificados (`all`, `page`, `pageAfter`, `count`, la familia `sumBy`, `maxRow`/`minRow`, `findWhere`/`countWhere`/`deleteWhere`, y el snapshot de `subscribe()`).
